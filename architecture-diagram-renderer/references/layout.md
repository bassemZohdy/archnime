# Layout and routing

Layout is derived from the portable model. The template uses the same decision rule at generation time and runtime so a diagram remains understandable if its model is regenerated by another AI tool.

## Choose the engine

1. Count incident edges per visible node. A high-degree node has more than 3–4 connections.
2. Estimate direction from source/sink structure: nodes with no incoming or no outgoing edges are evidence of upstream/downstream flow; reverse pairs reduce the score.
3. If the visible directed graph is acyclic, prefer a layered backbone for
   fan-out/reconvergence even when its hubs are high-degree. The engine derives
   deterministic ranks without special-casing domain IDs and keeps all
   supporting relationships in the route/validation graph. Choose ELK when the visible graph contains two or more package-parent
   levels. Its compound hierarchy is the stable signal; D3 remains the
   rendering and interaction layer. Choose dagre when most nodes are low-degree
   and the graph has clear direction. Choose D3 force when a substantial share
   (about 35% or more) is high-degree and the graph has weak endpoint structure
   or many reverse-direction relationships.
4. Use `meta.layout` or `stage.layout` to override the heuristic only when the
   architecture or presentation constraint warrants it. Record the reason in
   the model callout. ELK preparation is asynchronous and bounded by the
   expansion matrix; a missing runtime or unprepared interactive state falls
   back to dagre with a visible status message.

For dagre, use `rankdir: LR` for request/data paths and `TB` for a genuinely top-to-bottom hierarchy. Automatic cleanup treats those ranks as a primary-axis contract: overlap resolution and boundary/package clearance may move nodes across the secondary axis, but must not reverse upstream/downstream rank order. Fit expands or uniformly scales the logical union only after that ordering and containment pass. For ELK, use the layered algorithm with `elk.hierarchyHandling: INCLUDE_CHILDREN`, map expanded packages to parent nodes, and pass the density margin to node separation, between-layer separation, and padding. ELK is asynchronous, so the engine prepares the bounded expansion matrix once (`engine.ready`) and keeps `layoutStage()` synchronous for rendering, retries, and self-check. If an interactive presenter or package state falls outside that prepared matrix, the engine uses dagre for that state and the template surfaces the fallback in the status line; this is an intentional bounded-preparation tradeoff, not a silent engine switch. For force, stop the simulation after enough ticks to settle before calculating edges and labels. Always include a collision force whose radius is half the rendered node's largest dimension plus the density margin.
The **Tune layout** control evaluates up to three alternate deterministic
ELK layering/placement strategies crossed with the available wire-routing
strategies (curved, orthogonal, and direct) for the current stage and expansion
state. It evaluates three bounded objectives — `balanced` for general clarity,
`wire-clearance` for parallel-route separation, and `boundary-safe` for keeping
foreign blocks out of ownership zones. It reruns the shared route and label
passes for every candidate and keeps the lowest weighted self-check and
parallel-route-overlap and wire-readability score, so tuning can improve both
block placement and wire geometry even when every candidate has zero hard
findings. Each click adds bounded seeded multi-starts by varying ELK
child/edge order; later clicks can therefore discover a different clean
arrangement without making the result irreproducibly random. Package expansion
state remains stable and the selected wire mode and winning objective are
reported for that diagram. Retry variants are presentation state only; they
are keyed by stage, presenter mode, and expansion state and never mutate the
semantic model. Callers that need one objective can pass its `strategyId` to
`retryElk`. If the stage or model explicitly selects `manual`, the control
preserves those authored node positions and tunes only routes and labels; if
ELK is unavailable, the same control runs a bounded built-in layout/routing
search instead of disappearing.

## Portable heuristics from TALA and Graphviz

These notes capture useful placement ideas without adding either engine as a
runtime dependency:

- **TALA-style search:** treat layout as a bounded optimization problem over
  crossings, node distance, hierarchy readability, and label clearance. TALA
  documents that the objective is NP-hard and that heuristic search can land
  in materially different placements for different seeds, so keep a
  deterministic seed when reproducibility matters and retain the best scored
  candidate rather than trusting the first result. Its release notes also
  reinforce three priorities that fit this renderer: containers must grow for
  long labels, edge labels need overlap-aware placement, and several edges
  between the same nodes benefit from orientation-aware spacing. See the
  [TALA project](https://github.com/terrastruct/TALA) and its
  [release notes](https://github.com/terrastruct/TALA/releases).
- **Graphviz-style constraints:** use explicit layered direction (`rankdir`),
  same-rank constraints, and clusters when the author has supplied a genuine
  hierarchy. Graphviz treats clusters as subgraphs whose contents should stay
  inside a containing rectangle; this maps to our package parent semantics,
  while `contains` boundaries must remain a separate visual layer. Its
  [attribute reference](https://graphviz.org/doc/info/attrs.html) and
  [DOT language reference](https://graphviz.org/doc/info/lang.html) are the
  portable reference for these constraints.
- **Graphviz web transition lesson:** d3-graphviz performs a fresh Graphviz
  layout, extracts SVG data, then uses D3 joins to animate between layouts. It
  supports path/shape tweening and object-constancy key modes, but path and
  shape tweening can be computationally intensive. That supports keeping our
  fixed-topology `flow:` mode on one layout and making stage tweening an
  explicit opt-in rather than relayout-on-every-interaction. See the
  [d3-graphviz operation notes](https://github.com/magjac/d3-graphviz).

Portable policy derived from those references:

1. Preserve semantic IDs and author-supplied order as the initial seed.
2. Generate a small deterministic candidate set: direction, density margin,
   sibling separation, and package padding are the tunable dimensions.
3. Score every candidate using node/package/boundary overlap, edge crossings,
   label collisions, and canvas overflow; stop early only on zero findings.
4. Recompute routes and labels after the winning positions settle. Never use
   opacity, clipping, or an animation tween to conceal a geometric defect.
5. Keep parent packages in the layout graph, but keep cross-cutting boundary
   membership out of hierarchy constraints; otherwise trust scopes distort
   placement and become false containment.

## Density-based spacing

Do not use one global node gap. For each stage or nested package region:

- Find the busiest layer/region and cap its degree at 8 for stability.
- Convert that density into a margin between roughly 20 and 40 logical pixels.
- Keep visible wire geometry readable with `meta.minWireLen` (positive logical
  pixels; default 72). The effective value scales with the density margin and
  is exposed as `layout.spacing.minWireLen`. After layout, the renderer may move
  the lower-degree, unpinned endpoint by a bounded amount, then re-run
  deconfliction, package/boundary clearance, fitting, and routing. Manual and
  force layouts retain their authored/solver positions. For automatic ELK
  layouts, a top-level actor/gateway pair that would paint as a cramped knot
  receives a bounded gap-opening pass. Flat automatic layered layouts reserve
  `layout.spacing.readableWireLen` (about 120px before density scaling) plus
  marker clearance between ranks. This is physical space, not a minimum
  detour length; it does not silently rewrite semantic `minWireLen`.
  Pinned nodes are never moved by this pass; a surviving short edge in an
  enforced layout is reported as `wire-too-short`.
- Use rendered node width/height plus the margin as the default clearance. Feed the same margin into dagre `nodesep`/`ranksep`, force `forceCollide`, package padding, and label candidate distances. Package headroom and label lanes may add a small fixed allowance for text, but must derive their base from this margin.
- For nodes with more than three incident wires, reserve an additional label-clearance zone around the node. Derive the lane expansion from the local degree and density margin rather than a global pixel constant.
- Widen the logical canvas before reducing type size. Add height for extra ranks/rows. If the resulting canvas would make labels unreadable, split the diagram or use semantic zoom.
- For substantial flat directional backbones, the authored canvas is a minimum:
  final rank and boundary clearance may grow its logical width or height. The
  renderer updates the SVG viewport and minimum scroll width from that final
  layout; it does not write renderer coordinates or canvas growth into DSL YAML.
  When directional order pins an upstream foreign node, or a foreign expanded
  package outline, against a trust envelope (so that pushing it upstream would
  reverse its rank, or its padding reaches the envelope), open the gap
  downstream instead: translate every node past it along the rank axis and let
  the canvas grow. A package outside a boundary's scope keeps the same
  clearance outside the envelope that a member package keeps inside it; the
  self-check reports a shortfall as `boundary-package-gap`.
- Text is measured from a pinned advance table for the embedded Inter Variable
  font (`scripts/gen_font_assets.mjs`), never from the host canvas, so every
  number in this contract is the same on every platform. Perspective emphasis
  must not change text weight or size, because layout reserved the measured
  space; use colour, stroke, or underline.
- Keep any boundary/depth reserve below the canvas's minimum usable inner width/height; a retry must widen clearances without squeezing all nodes into a narrow strip.
- Keep the hierarchy visually legible by allocating spacing in layers: rendered node clearance, package outline padding, then boundary-zone inset. Boundary inset must be larger than package padding by a density-derived gap; this keeps a trust/compliance envelope from sitting directly on a package or block.
- After boundary separation and node deconfliction, repeat the package-clearance pass for nested layouts and recompute boundaries before routing wires or placing labels. A free-standing block that is clear before boundary movement can otherwise drift back inside an ancestor package's padded outline when a child package expands.
- After those passes settle, fit the whole layout: translate every node so the union of node, package, and boundary rectangles clears the edges. Flat directional backbones grow the logical canvas when that union is larger than its authored minimum, preserving real node sizes and rank gaps. Other layouts may uniformly scale node positions about the content centre. Explicit legacy boundary rectangles move with the nodes; computed boundaries are re-resolved afterward. Re-resolve boundaries, packages, and labels from the fitted nodes.
- Leaf node boxes auto-size to their text: the renderer grows a node's width to fit its detail line and its longest single label word, up to a 300px cap, mirroring the package-block caption grow. A `size` override only raises the floor; past the cap the `detail-overflow`/`label-truncated` finding stands and the text must be shortened.
- Boundary rendering under collapse (`resolveBoundaries`): a boundary whose entire visible scope has collapsed into a subset of — or the same block as — another boundary's scope, while the two are disjoint in the model, is drawn as a **tag/pill on the shared block(s)** (`chip: true`, rendered in `gBoundChips`) instead of an enclosing rectangle that would read as false containment. Two disjoint scopes that keep exclusive members but collide on a shared collapsed block have their exclusive members separated (Venn overlap, not swallow). Genuine cross-cuts (shared model leaf) stay overlapping; a real model strict-subset still nests (outer wider inset). Free-standing non-member nodes are pushed out of boundary rectangles, including under `force`. Collapse is never blocked.

The template keeps positions for stable IDs as force seeds, but the model—not cached positions—is authoritative. Nodes in both endpoint stages should have the same semantic ID and, where possible, the same region so layout changes do not imply a false architectural migration. The renderer uses a bounded retry loop per stage/state: it restores one seed, progressively widens spacing, scores geometry and label findings, stops at zero findings, and retains the best trial. Set `meta.layoutValidation.maxTrials` to tune the budget (default 12, hard cap 32); never replace it with an unbounded relaxation loop.

## Edges and labels

- Use a cubic Bézier curve when parallel edges share a pair or when endpoints are close. Keep every curved endpoint tangent axis-aligned and perpendicular to the actual rendered block face, spread the paired detour through the middle of the path, and preserve direction and arrowheads. The curve endpoint must land on the rendered block silhouette (including its actual exit/entry face); do not leave a fixed gap before the arrow tip. For ELK-generated positions, keep the endpoint lane stable while searching both sides of the chord; do not accept a curve that crosses an unrelated node, package, or boundary. Every reroute pass must retain the same obstacle context, including the minimum-wire-length correction pass.
- Orthogonal routing prefers a clear straight connection between aligned
  facing ports, or a monotone Z between staggered facing ports. Add detours
  for obstacles, not to meet a wire-length quota. Layer spacing and the
  minimum-wire-length correction pass must create physical endpoint space;
  keep constrained manual/force positions unchanged and report any enforced
  residual shortfall. Tune measures endpoint separation and penalizes excess
  route length and bends so a decorative loop cannot improve readability.
  From a clean baseline, Tune must also preserve already-cramped endpoint
  clearance; it may reduce surplus whitespace above the readability floor.
- Calculate node positions first, then edge geometry, then labels. Label placement must use the settled curve, test both sides and several curve positions, and report a collision when no candidate is clear.
- Candidate distances should expand with the local endpoint degree and use the density margin. Search dedicated lanes before falling back to a collision report; do not silently place a label through a busy node.
- Treat the rendered node silhouette, including database ellipses, queue rails,
  and actor pill ends, as the endpoint geometry. Reserve both the node body and its label
  zone as obstacles; a label over either endpoint is reported as
  `wire-label-over-endpoint`.
- Keep edges out of unrelated blocks. Move a node or change a rank before adding a manual offset.
- Active flow is an animated dashed overlay on the semantic wire. Stagger each flow's animation delay by a small deterministic amount (for example, based on wire order), not a random value.

## Wire routing mode

`meta.routing` selects how wires are drawn. `curved` (the default, and the
only mode for `transition-diagram/1.0` unless opted in) is the cubic Bézier
described above. `orthogonal` routes each wire as a horizontal /
vertical polyline:

1. **Straight** — endpoints aligned within a few px and the segment is
   clear: a single H or V line.
2. **L** — one right-angle bend, exiting each node on the face toward the
   other.
3. **Z** — a mid H/V segment; the router walks a face-plan and mid-shift
   ladder to miss obstacles.
4. **Diagonal fallback** — the `curved` quad, tagged `orthogonal-fallback`
   and reported as the advisory `edge-route-fallback`.

Every face-plan must lead out along the source face normal and lead in along
the target face normal before joining the middle Manhattan route. This is
especially important for mixed-axis plans such as bottom → left: the final
segment must enter the target horizontally, never run along its side, so the
arrowhead points into the block.

When multiple orthogonal wires leave or enter the same block face, allocate
deterministic ports along that face before routing. Keep this port offset
separate from the lane offset used for parallel edges between the same pair;
two incident wires must not share a long collinear segment before they diverge.
`requestedRouting` is the viewer's selected family; `actualRouting` is derived
from the painted geometry. A fallback reason is required whenever those differ.
Classify by shape, not by data structure: a Bézier is `curved`; a polyline is
`orthogonal` only when every segment is axis-aligned. A Direct route is a
polyline too (face-normal lead-in and lead-out around a diagonal run), so it
reports `direct` and is not a fallback.

Obstacles for `orthogonal` routing are unrelated node rectangles **plus**
package outlines and computed boundary rectangles. Curved routing applies the
same package/boundary ownership rule while searching both control-point sides.
A container rectangle is transparent to a wire whose own endpoint sits inside
it (the wire may leave its container). The self-check reports
`edge-crosses-package` and `edge-crosses-boundary` for any settled curved or
orthogonal path that enters a rectangle that holds neither endpoint. If no
clear curve exists, the renderer uses the collision-aware orthogonal router for
that wire and records `edge-route-fallback`; a container-crossing fallback is
still reported rather than hidden.

Switching the wire style in the viewer (or calling `engine.setRouting`) is a
presentation change, not a placement request. The engine reroutes every
settled layout in place: node boxes, package and boundary envelopes,
expansion state, and committed **Tune** placements are kept, while routes,
ports, jumps, reverse paths, and labels are recomputed. Returning to a style
reproduces that style's earlier wire geometry. Placement is recomputed only by
an explicit layout action (Tune, expansion change, or a media/print refresh).
Any constraint the new style cannot satisfy on the kept placement is reported
per wire through `actualRouting`/`routeFallbackReason` and by the self-check,
not hidden by moving nodes.

`meta.wireJumps` (`arc` default, `gap`, `none`) draws a small hop where two
different orthogonal wires cross without connecting. The higher-`order`
wire goes under and takes the hop; the animated flow overlay is drawn from
the un-hopped `linePath` so the dash is undisturbed. Curved mode does not
draw jumps.

## Secondary-flow routing and disclosure

The permanent wire types remain `data`, `security`, `control`, `compat`, and `neutral`. Presentation policy may identify `control` and `neutral` routes as secondary and either de-emphasize them or place explicitly grouped secondary routes in a shared lane. A bundle name is a semantic grouping hint, not permission to change endpoints or invent a new flow type; it does not lock the route to Curved when the viewer selects Orthogonal or Direct. Primary data paths remain individually readable.

When a stage is dense, use its optional `disclosure` sequence to reveal `primary` wires first and supporting `secondary` wires afterward. This within-stage sequence is independent of a current-state/target-state transition. Layout and self-check still account for all wires so revealing a layer does not move the architecture unexpectedly.

## Nested package layout

Collapsed packages occupy one semantic node. When a package is expanded, its children take part in the **single global layout pass** for the stage; the renderer then draws a padded dashed outline around wherever those members settled. There is no separate sub-layout per package. Two aids keep members together: dagre and ELK lay expanded packages out as compound/parent clusters, and after either engine a light pass pulls each expanded package's members toward their shared centroid and pushes overlapping sibling clusters apart. Nested bounds are still computed recursively so each heading gets its own headroom, and a one-member expanded package draws no outline.

These aids reduce overlap; they do not eliminate it for adversarial models. The self-check reports `package-overlap` when two sibling outlines intersect. It evaluates a bounded expansion matrix per stage: default, collapsed, configured, each package, nested level combinations, pairwise combinations, and all-expanded, capped by `meta.layoutValidation.maxExpansionScenarios` (default 20, hard cap 32). Each state is retried from a stable seed with at most `meta.layoutValidation.maxTrials` trials. For a tagged finding, first widen the density margin (feeds dagre `nodesep`/`ranksep`, ELK separations/padding, force `forceCollide`, and package padding together — see Density-based spacing above) before concluding the model is over-grouped. Only when wider spacing would blow up the canvas or shrink labels below readability does it mean the model is asking for more grouping than a flat layout can show at once — expand fewer levels, re-group members that sit near each other, split a package that spans the whole flow, or move deep C4 detail into its own stage. `force` layout tolerates at most one nested package; beyond that use `layout: manual`.

## Deployment layout profile

The v2 deployment translator derives physical instance IDs from logical
placements, then represents each infrastructure node as a deployment package
with `deploymentKind`. The engine selects its explicit `deployment` profile
for that normalized stage: it orders instances deterministically by
infrastructure target, placement, and replica, lays out the compound
region/cluster/host tree, and runs the same containment, routing, label, and
canvas checks as logical packages. Deployment outlines are styled separately
so a host cannot be mistaken for a catalog component or logical package.

A placement is not a relationship. The engine only fans out a wire when its
logical endpoints both have placements; it never invents connectivity from
shared hosts. Keep the infrastructure tree acyclic, target leaves, and use a
stable replica count/order so `${component}@${target}#${index}` IDs remain
portable across regenerated models.

## Engine decision and maintenance

ELK is pinned to `elkjs@0.12.0` in the template and translator. The backend
policy is: ELK for nested compound graphs, dagre as the flat layered/default
fallback, and force for peer meshes. The renderer's parity harness runs every
model through dagre and ELK and fails when ELK introduces a new self-check issue
class. D3 remains the presentation layer rather than a competing semantic
layout source. This repository's pinned dagre IIFE integration is
maintenance-only, even though the upstream [`@dagrejs/dagre`](https://github.com/dagrejs/dagre)
project continues to publish modern releases; retain the synchronous fallback
for missing runtimes and bounded interactive states.

A related, separately-checked failure: a free-standing node that is **not** a package member can still end up rendered inside an expanded package's outline, because the post-layout push that tries to clear it can lose to the canvas-edge margin reserved for deep nesting — most likely when the outermost package already spans most of the canvas. The self-check reports this as `package-contains-foreign-node` (`references/validation.md` has the fix order: widen the canvas first for `dagre`, consider whether the node is honestly a member, then fall back to `layout: manual` — canvas widening is markedly weaker for `force` layout specifically, since the simulation settles in its own space before being rescaled to fit the canvas).

Boundary envelopes follow the same hierarchy rule. The template gives a computed boundary more inset than a package outline, draws boundaries behind packages and nodes, and separates disjoint boundary member groups before recomputing their envelopes. It also pushes a node clear of a boundary when that node is exclusive to another boundary; only a genuine shared member stays in both envelopes. Boundary titles are placed from a bounded candidate list after member positions settle, avoiding nodes and earlier boundary titles where possible. Shared-member boundaries are allowed to remain cross-cutting because moving the shared node would violate both scopes; in that case only title collisions and an exclusive node touching the other envelope are defects. A `boundary-gap` finding means two disjoint computed envelopes still touch or overlap. A `boundary-package-gap` finding means a boundary exactly wraps a package but does not leave the required inner clearance. If collapse makes a disjoint boundary's visible scope a subset of another boundary's scope, the smaller/equal scope is rendered as a compact dashed chip on its visible host block. Chip geometry uses the current Presenter font, participates in label obstacles, stays pointer-transparent, and is checked for `boundary-chip-overflow` and `boundary-chip-collision`. Fix these in the renderer layout policy first; do not add hand-tuned coordinates to the DSL.

Package and boundary captions are layout geometry too: reserve enough package width and computed-boundary width for their full labels, keep each caption inside its outline, and place package captions against both node and boundary-title obstacles. A caption that cannot fit is a layout issue, not a cosmetic overflow to ignore; report `package-label-overflow` or `boundary-label-overflow` rather than clipping it.

## Boundaries and responsive sizing

Boundaries represent ownership, trust, or deployment — not structure (that is packages). Prefer `contains: [ids]` so the rectangle is computed from the settled member positions each stage; explicit `{x, y, w, h}` drift and usually trip `boundary-straddle`. A boundary whose members equal a package's is useful only when it communicates an outer trust/compliance zone; it must have visibly larger inset than the package. Disjoint boundaries should be separated after layout; boundaries with shared members may cross-cut and overlap semantically. The self-check reports `boundary-straddle` when a listed member is not fully inside, or a non-member sits mostly inside; `boundary-gap` for touching disjoint envelopes; `boundary-package-gap` for a package that loses its outer-zone breathing room; `boundary-chip-overflow`/`boundary-chip-collision` for degenerate collapse tags; `edge-crosses-node` when a settled wire enters an unrelated visible node; and `stage-overflow` when geometry leaves the logical canvas. Use SVG `viewBox` coordinates with CSS width `100%`; on narrow screens, keep page overflow inside a bounded diagram scroller and use the model's logical minimum width only when labels need it. Reflow the surrounding shell to one column and keep controls touch-sized. Verify at 1280px, 900px, a narrow viewport, and a print viewport. On a wide screen the diagram is also height-capped (`--canvas-max`, roughly `100svh` minus the header/controls chrome) with `preserveAspectRatio="xMidYMid meet"`, so a tall auto-height render scales down to keep the controls bar on screen instead of pushing it below the fold; the mobile breakpoint clears the cap because that view already scrolls the diagram horizontally.

When computed boundaries share members while each also has exclusive members (a genuine cross-cut), the renderer gives their envelopes deterministic visual lanes by expanding successive boundaries outward. The extra rail separation keeps coincident corners and edges readable without moving shared nodes or changing `contains`; the larger envelope is a paint-space lane, not a hierarchy claim. Boundary-title candidates also avoid the rails of neighboring envelopes, moving a title to a lower or opposite-side lane when the top rail is occupied.

A boundary's own padding around its members is deliberately larger than a package's headroom around its members (both derive from the density margin, but the boundary constant carries a bigger fixed offset on top). This is not just visual breathing room: a boundary is explicitly allowed to wrap a package's exact membership (a compliance scope that happens to equal a package's contents), and when it does, both shapes' top-left corners are computed from the same topmost/leftmost member. If the two paddings were similar, the two corners — and the clickable title text anchored at each — would land within a few pixels of each other regardless of how the members are otherwise spaced out; widening the canvas does not help because it scales both shapes' distance from that shared corner together. The self-check reports this as `package-boundary-label-collision`; if it fires, the fix is almost never the model — it means the boundary padding constant has regressed toward the package's, not that this particular diagram needs different member placement.
